# connection 10.0.0 — implementation plan

**Spec:** `docs/superpowers/specs/2026-09-30-connection-10-design.md`, answering to the goal
`docs/superpowers/2026-09-30-connection-10-goal.md` (rules H1–H7). Both are read before any task.

**How the tasks run:** each task is test-first — the tests named in the task are written, seen red, the
change is made, the tests go green, the whole suite stays green, then one commit. After the tests pass,
the task's load-bearing checks are run: the named rule is broken on purpose, the named test must turn red,
the rule is restored. Code appears at implementation; this plan names what changes, where, in what order,
and what each test must prove.

## Global constraints

- `@mcp-abap-adt/interfaces-auth` `^3.0.0`; `@mcp-abap-adt/interfaces-auth-sap` `^1.1.0`;
  `@mcp-abap-adt/auth-providers` `^5.0.1` in **devDependencies only** (H6).
- Nothing in `src/` outside tests branches on the provider's `kind`, narrows it, or reads
  `config.username` / `config.password` to authenticate (H1, H2).
- After Ok from `rejected()`: exactly one more attempt; a second refusal is the verdict (H5).
- Fixed wordings, verbatim from the spec: `the credential provider failed`;
  `the credential was refused again after the provider renewed it`;
  `this wire takes no logon parameters (HTTP)`; `this wire carries no TLS material (RFC)`;
  `this connection has no credential to renew`.
- The repo's conventions (CLAUDE.md): `.js` suffix on local imports, `node:` built-ins, Biome formatting.
- The version becomes `10.0.0` only in Task 7.

## Review focus — what no single task's tests catch unless asked for

1. A consumer's provider that **throws** instead of answering → Oops "the credential provider failed", the
   throw as cause; never an unhandled rejection. (Task 2)
2. **Concurrent requests meeting the same 401** → each asks `rejected()` once and resends once; none loops
   or hangs. (Task 3)
3. **A 401 inside a critical section** (lock held) → resend on the same session, no `SESSION_REPLACED`.
   (Task 3)
4. **An RFC per-call logon failing mid-session** (SNC client logged out after connect) → the provider gets
   the raw SDK error at `logon`, the caller gets its words. (Task 5)
5. **TLS material that changes between logons** → the next request uses a new agent; the cookie jar
   stays. (Task 4)

## Task 1 — The contract switch

**Why first:** bumping `interfaces-auth` to 3.0 breaks the package's own 2.x providers, so the bump, their
removal and the connection calling the 3.0 provider are one compile unit.

**Steps**
1. Bump `interfaces-auth` and `interfaces-auth-sap`; add auth-providers as a dev dependency.
2. Tests first for the two new modules:
   - `AuthRefusedError` carries refusal, moment and cause; its message is the reason with the hint.
   - `WireLogonError` keeps the raw error as it arrived (same object) and the status.
   - `guarded`: an outcome passes through; a throw becomes `PROVIDER_FAILED` with the throw kept.
   - `requestTargetOn`: `header()` writes and replaces; `cookies()` merges into `Cookie`, the credential
     winning a repeated name; sets `Cookie` when there was none.
3. Write `authErrors.ts` and `requestTarget.ts`.
4. `CredentialAbapConnection`: `prepareCredential` calls `prepare()` through `guarded`, an Oops throws
   `AuthRefusedError('prepare')`; the request headers get what `authorize()` writes, through `guarded`, an
   Oops throws `AuthRefusedError('request')`. Remove `getHttpsAgentOptions` and `isUnauthorized`.
5. Delete the four source files and their tests (`FileCertificateMaterialLoader`, `ntlm`), and the two
   tests of the 2.x contract (`renewableCredential`, `credentialContract`) — their behaviour is re-covered
   against 3.0 in Tasks 2–6.
6. `index.ts`: drop the provider and loader exports; export `AuthRefusedError`, `WireLogonError`,
   `AuthRefusalMoment`.
7. Migrate the tests: provider imports come from `@mcp-abap-adt/auth-providers`; `new TokenAuthProvider(x)`
   becomes `.fixed(x)` / `.from(refresher)`; hand-written 2.x credential stubs become 3.0 providers that
   write the same header or cookies; cases asserting that `transportMaterial` reaches the agent are
   deleted (Task 4 re-covers TLS); the test helper that builds an on-prem HTTP transport stops reading TLS
   from the credential.
8. The three scripts that import `BasicAuthProvider` from `../dist/auth/providers`
   (`scripts/pr41-rfc-lock.ts`, `pr41-onprem-verify.ts`, `onprem-session-hold.ts`) take it from
   `@mcp-abap-adt/auth-providers` — `npm run build` type-checks `scripts/` (`typecheck:scripts`), so this
   belongs here, not in Task 7.
9. Build (with its scripts type-check) and full suite green; commit.

## Task 2 — The lifecycle's credential hooks

**Steps**
1. `stubProvider` test helper (shared names table).
2. Tests first, on a connector with a stub provider:
   - `credentialHeaders` writes `X-SAP-Client`, then the provider's header;
   - an `authorize` Oops → `AuthRefusedError` at `request` with the provider's refusal;
   - a `prepare` Oops → `AuthRefusedError` at `prepare`;
   - an `establish` Oops → `AuthRefusedError` at `logon`, and `rejected` is **not** asked;
   - `credentialRejected` hands the rejection to the provider unchanged and returns its answer;
   - a provider that throws → `PROVIDER_FAILED`, the throw as cause;
   - the base class alone writes nothing and answers `NO_CREDENTIAL_TO_RENEW`.
3. `AbstractAbapConnection`: add the three hooks and `credentialHeaders`; `getAuthHeaders()` becomes
   "empty record through `credentialHeaders`"; remove the abstract `buildAuthorizationHeader`,
   `getHttpsAgentOptions`, `recoverSession`, `discardSession`, and the comment that places renewal in a
   wrapper that does not exist.
4. `CredentialAbapConnection` overrides the hooks (provider calls through `guarded`) instead of
   `getAuthHeaders`.
5. Test subclasses that implement `buildAuthorizationHeader` override `authorizeRequest` instead.
6. Load-bearing: moment `logon` swapped for `request` → the establish test fails; `guarded` removed from
   `prepare` → the throwing-provider test fails.
7. Full suite green; commit.

## Task 3 — A request: authorize every attempt; a surviving 401 → `rejected()` → one more attempt

**Steps**
1. `startSapStub` test helper (shared names table), CSRF-enforcing.
1a. The HTTP wire names a refused logon (moved here from Task 4, because this task's token-fetch cases need
   it): tests first — a 401 from the establishing request surfaces as `WireLogonError` with status 401 and
   the wire's error as its cause, after the refusal's cookies are folded in; a 500 is still retried as
   today. Then `HttpTransport.establish` turns a 401 into `WireLogonError(error, 401)`. Until Task 4 wires
   `rejected()` into `connect()`, a 401 at connect surfaces as that `WireLogonError`: migrate
   `connection/sessionComposition.test.ts` "a credential refused while establishing" to expect it (Task 4
   rewrites it to the renew-then-connect case).
2. Tests first, on a real `OnPremHttpTransport` against the stub, connected with a stub provider. A GET 401
   is first retried by the wire itself when the session's cookies are held (path b), so a 401 reaches the
   provider only when it comes twice:
   - two 401s → `rejected` asked once with `at: 'request'`, `status: 401`; the resend returns 200 and
     carries `Stub 1`;
   - `rejected` Oops → `AuthRefusedError` at `request` with the provider's words, the 401 as cause;
   - three 401s → `REFUSED_AGAIN`, `rejected` asked once;
   - 403 → thrown unchanged, `rejected` never asked;
   - a stale CSRF 403 on a POST → cured by the wire, `rejected` never asked;
   - the wire's own resend (path a) carries a newly authorized header, not the first attempt's;
   - a POST whose stale CSRF 403 sends the wire to fetch a token, and the fetch meets a 401 → `rejected` at
     `logon` with status 401, not the original 403; Ok → the token fetch runs again, the POST goes out with
     the newly issued token and ends 200; `rejected` asked once;
   - the same, but the second token fetch meets a 401 too → `REFUSED_AGAIN`, `rejected` asked once;
   - a POST whose CSRF recovery resends, and the resend meets a 401 → `rejected` at `request`, not the 403;
   - a POST whose CSRF recovery resends, and the provider says no when re-authorizing it →
     `AuthRefusedError` with its words, not the 403;
   - a GET whose path-(b) token fetch meets a 401 → `rejected`, not the original error;
   - two concurrent requests, each meeting two 401s → each asks `rejected` once, both end 200;
   - inside `beginCriticalSection()` / `endCriticalSection()`, a surviving 401 → resend on the same session
     (fingerprint unchanged).
3. `performRequest`: the headers come from `credentialHeaders` per attempt; each resend in paths (a) and (b)
   is re-authorized first; the existing catch body moves into a "recover on the wire" step with one change:
   where a failed retry now throws the ORIGINAL error (path a's retry catch) or is swallowed (path b's
   token-fetch catch), an `AuthRefusedError`, a `WireLogonError` or a 401 from the retry is thrown instead —
   after the session verdict, which still comes first. What survives the step is classified — `WireLogonError` → a `logon` rejection with the raw cause, a 401 → a
   `request` rejection, anything else rethrown — and a rejection goes to `credentialRejected`: Oops →
   `AuthRefusedError` with the provider's words; Ok → the one more attempt, on the same lease:
   - after a `request` rejection: re-authorize, resend;
   - after a `logon` rejection: the wire logged on anew is made ready first — its token dropped and
     established again, as the upfront mutation step does (a no-op on RFC) — then the new token and the
     wire's cookies go onto the request, re-authorize, resend.
   The fetch and the resend share the one limit: a credential failure in either → `REFUSED_AGAIN`.
4. Load-bearing: no re-authorization before the resend → "carries `Stub 1`" fails; no token fetch after a
   `logon` rejection → the "newly issued token … 200" test fails (the stub answers 403); a 401 at
   establishment not turned into `WireLogonError` → the token-fetch tests fail; the retry catches
   throwing the original error again → the four CSRF-recovery tests fail; 401 not classified → the
   `rejected` tests fail; 403 classified as the credential's → the 403 test fails; asking `rejected` again
   on the second failure → the `REFUSED_AGAIN` test fails.
5. Full suite green (recovery-path, fencing and critical-section suites included); commit.

## Task 4 — The session context and HTTP

**Steps**
1. Tests first, against the stub SAP:
   - connect calls `prepare`, then `establish`, then `authorize` for the establishing request;
   - a `prepare` Oops sends nothing and `establish` is never called;
   - the HTTP logon target takes TLS material (Ok) and refuses logon parameters with the fixed wording;
   - the agent is built from the material the logon offered, over the constructor's `agentOptions`;
   - the same material keeps the client; different material rebuilds it; the cookie jar survives;
   - a 401 at establishment → `rejected` at `logon` with status 401; Ok → a second `establish`, connected;
   - the same with Oops → `AuthRefusedError` at `logon` with the provider's words;
   - two 401s at establishment → `REFUSED_AGAIN`, `rejected` asked once;
   - a 500 at establishment is retried by the wire as today and never reaches `rejected`;
   - the logoff is authorized.
2. `IAdtSessionContext`: `authHeaders` gives way to `authorize(headers)` and `logon(target)`; the lifecycle
   builds them from `credentialHeaders` and `logon`, for the session context, the CSRF fetch and the
   establishment alike.
3. `connect()`: `prepareCredential` before the wire opens (and out of `establishAndCommit`); open +
   establish as one step; a `WireLogonError` from it → `credentialRejected` at `logon`; Ok → the step once
   more; Oops → `AuthRefusedError`; a second `WireLogonError` → `REFUSED_AGAIN`.
4. `HttpTransport`: `logonTarget()` as in the spec §4.1 (material compared by value; a change drops the
   cached client); `open()` calls `context.logon(logonTarget())`; the agent merges `agentOptions()` and the
   material; `establish` fills its headers through `context.authorize` and lets an `AuthRefusedError`
   through untouched (its 401 → `WireLogonError` is Task 3's). `sessionComposition.test.ts` "a credential
   refused while establishing" becomes: a 401 at establishment, a provider that renews → connected on the
   second logon.
5. `CloudHttpTransport.open` calls the base `open` first, outside its swallowing `try`, and lets an
   `AuthRefusedError` through; its `close` and `OnPremHttpTransport.close` fill their headers through
   `context.authorize` and stay silent on failure. `LegacyOnPremHttpTransport` inherits `open`.
6. Migrate the tests and the stub-transport helper that build a context with `authHeaders`.
7. Load-bearing: no logon in `open` → the order test fails; the dropped client kept → the rebuild test
   fails; `connect()` not catching `WireLogonError` → the three logon-refusal tests fail; `prepare` after `open` → the
   "never calls establish" test fails.
8. Full suite green; commit.

## Task 5 — RFC

**Steps**
1. Tests first, with a fake conversation factory that records each open's parameters and can refuse chosen
   opens with a given raw error:
   - the parameters the provider writes go into the open (`user`/`passwd`; the four SNC keys unchanged);
   - the RFC logon target refuses TLS material with the fixed wording;
   - a failed open is a `WireLogonError` whose cause is the raw error object;
   - a per-call conversation logs on too (one logon per open);
   - `rfcParamsFrom` returns the address only and needs no user or password;
   - through a connector: a refused open at connect → `rejected` at `logon` with the raw error; Ok → one
     more open; Oops → `AuthRefusedError` in the provider's words;
   - a per-call open refused after connect → `rejected` at `logon` with the raw error, then one resend, 200;
   - an `establish` Oops ends the connect in its words; `rejected` never asked.
2. `rfcConversation.ts`: `RfcConnectionParams` and `rfcParamsFrom` keep only the address; the factory from
   `rfcConversationFrom` takes the logon parameters and spreads them over the address.
3. `RfcTransport`: the factory takes the logon parameters; `open(context?)` keeps the context's `logon`
   (optional, so a wire can be driven without a lifecycle); one private "logged-on conversation" step —
   build the target, ask `logon`, open, wrap a failed open in `WireLogonError` with the raw error — used by
   the session's open and by every per-call open.
4. Migrate the RFC tests: `'Failed to open RFC connection'` expectations become `WireLogonError` with the
   raw cause; `rfcParamsFrom`'s username/password expectations go.
5. Load-bearing: re-wrapping the error → the two "raw" tests fail; skipping the logon on per-call opens →
   the per-call logon test fails; `user` back in `rfcParamsFrom` → the address-only test fails.
6. Full suite green (live RFC suite skips without its env file); commit.

## Task 6 — The contract over the real providers

**Steps**
1. `realProviders.test.ts`, over auth-providers' providers, with nothing branching on which provider it is:
   - basic and a fixed token over HTTP: connect, the work request carries `Basic …` / `Bearer …`; three
     401s end in the provider's own refusal;
   - certificate over HTTP: its material reaches the agent at logon;
   - basic over RFC: the open gets `user`/`passwd`; a refused open ends in "the user or password was
     refused";
   - certificate over RFC: refused at logon in its words (the RFC target refuses TLS);
   - a bearer token over RFC: the open gets no parameters and the connect ends in `AuthRefusedError`;
   - SNC over RFC: `SncLogonProvider` with an injected `ISncLibraryLocator` (or `DefaultSncLibraryLocator`
     over a fake `SncSystem`, both exported by auth-providers) and no probes — the open gets `snc_mode` `1`,
     `snc_partnername`, `snc_qop` (default `9`), `snc_lib` from the locator, and `snc_myname` when `myName`
     is given; a refused open whose raw SDK error is `RFC_COMMUNICATION_FAILURE` with `A2200019` in its
     message ends in "the SNC library has no credential to present (A2200019)" — the raw error reaching the
     provider unwrapped.
2. Load-bearing: a branch on `kind === 'basic'` in the logon hook → the basic-over-RFC test fails; the RFC
   open error re-wrapped in a new `Error` → the SNC `A2200019` test fails.
3. A failing case is fixed in the task that owns the behaviour, not here. Commit.

## Task 7 — Documentation and release metadata

**Steps**
1. `docs/MIGRATION-10.0.md`: providers from auth-providers (and the token factories); TLS no longer wired
   by hand (`agentOptions` stays for `ca` / `rejectUnauthorized`); RFC — the factory takes the logon
   parameters, config's username/password are not read; catching `AuthRefusedError`; a custom wire —
   `authorize` / `logon`, `WireLogonError`. Each with a before/after example.
2. README and every doc that imports a provider from this package; `docs/USAGE.md`'s refusal section
   rewritten from spec §3.3 (each request asks the provider; renewing providers share one renewal); the
   other docs listed in spec §8; `CLAUDE.md`'s architecture section.
3. `examples/` take providers from auth-providers (the scripts moved in Task 1).
4. `CHANGELOG.md` 10.0.0 (Breaking, Added, Removed, Fixed); version 10.0.0.
5. Build, lint, full suite, docs-path test green; commit.
